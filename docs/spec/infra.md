# Generated infrastructure

`dynaflux generate` writes a store's AWS infrastructure as CloudFormation templates in
`infra.out` (default `infra/dynaflux`). This page is their reference: every resource, its
name and settings, the IAM permissions, the alarms, and how to deploy and change them.
Dynaflux never deploys anything itself: you deploy the templates with the SAM CLI or your
own pipeline.

The inputs are `dynaflux.yaml` ([config.md](config.md)) and the SQL files
([sql.md](sql.md)); what the tables hold is in [encoding.md](encoding.md). Two decision
records explain the less obvious parts:
[ADR 0003](../decisions/0003-shard-identity-from-tumbling-window.md) (the event source
mapping) and [ADR 0008](../decisions/0008-archive-schema-migration.md) (the archive schema
and the setup function).

## 1. Files and stacks

| File | Deploy it | It holds |
|------|-----------|----------|
| `global.yaml` | Once, in one region of `regions`: the **home region**. The global stack stays there for the life of the store. | One DynamoDB Global Table per stream, with a replica in every region of `regions`. |
| `global.stack-policy.json` | Once, on the global stack, after its first deploy. | A stack policy that forbids replacing a stream table, including those of streams added later. |
| `regional.yaml` | In every region of `regions`, after `global.yaml`. | The meta table, the view tables, an S3 bucket, the Lambda functions, one event source mapping per stream, the archive, alarms and a dashboard. |

There are two templates because CloudFormation manages a Global Table, with all its
replicas, from one stack in one region.

- `regional.yaml` uses the SAM transform (`AWS::Serverless-2016-10-31`), only for its
  Lambda functions, so that `sam build` compiles the runtime binary. `global.yaml` is plain
  CloudFormation.
- Every function runs the one binary built from `runtime.out`, and the environment variable
  `DYNAFLUX_MODE` tells it what to do. These templates use two modes: `projector` applies
  stream records to the views and the archive, and `setup` answers CloudFormation's
  deploy-time requests ([§6.2](#62-stream-arn-lookup), [§7.2](#72-archive-schema)). The
  `backfill` mode arrives in M5 and `query` in M6 ([§15](#15-not-in-these-templates-yet)).
- The YAML files start with `# Code generated by dynaflux <version>. DO NOT EDIT.`
  `generate` doesn't overwrite a file in `infra.out` that lacks this line. The stack policy
  is plain JSON and can't carry it, so `generate` overwrites the policy only when the
  `global.yaml` next to it carries the line, or when neither file exists.
- The same inputs give the same bytes, so the templates can be committed and reviewed as
  diffs. They have no outputs: every name is derived ([§3](#3-names-tags-and-logical-ids)).

## 2. Parameters

| Parameter | Template | Default | Meaning |
|-----------|----------|---------|---------|
| `Prefix` | both | `prefix` from `dynaflux.yaml` | The prefix of every resource name. |
| `LookupGeneration` | `regional.yaml` | `1` | Change it to make the stream lookups run again ([§6.2](#62-stream-arn-lookup)). |
| `AlarmTopicArn` | `regional.yaml` | empty | The SNS topic that receives alarm notifications. |

**`Prefix`** lets one set of templates, generated from one checkout and one `dynaflux.lock`,
serve every environment of a store: deploy them with `Prefix=staging-` for a staging copy,
for example. The functions get the prefix in `DYNAFLUX_PREFIX`, so the binary is the same in
every environment.

- `MaxLength` is the longest prefix with which every name in the templates stays within its
  AWS limit, in every region of `regions` and with a 12-digit account ID. CloudFormation
  refuses a longer prefix before it creates anything. `validate` checks the names with the
  `prefix` in `dynaflux.yaml` ([config.md](config.md#resource-names)).
- `AllowedPattern` is `^(?!xn--|sthree-|amzn-s3-demo-)([a-z][a-z0-9-]*-)?$`: empty, or the
  form `prefix` takes in `dynaflux.yaml`, and not starting with a prefix that S3 reserves
  for bucket names.
- Use the same value for the global stack and the regional stacks of one environment.
- A stack's prefix is fixed for its life: a new prefix means new stacks
  ([§12](#12-changes-after-the-first-deploy)).

**`AlarmTopicArn`:** when set, every alarm sends its `ALARM` and `OK` notifications to this
topic, which must be in the stack's region. When empty, the alarms still change state and
show on the dashboard, but notify no one. Dynaflux doesn't create a topic. Use one that
CloudWatch can publish to: a topic encrypted with the AWS managed key for SNS drops alarm
notifications without an error.

## 3. Names, tags and logical IDs

Names derive from `prefix`, `store` and the SQL names. In the table, `{base}` is
`{prefix}{store}`. The examples use `prefix: prod-`, `store: analytics`, the stream
`page_views`, version 2 of the view `page_daily`, the account `123456789012` and the region
`us-east-1`. [config.md](config.md#resource-names) gives each name's AWS limit and the
length budget that `validate` checks.

| Resource | Name | Example |
|----------|------|---------|
| Stream table (global) | `{base}-stream-{stream}` | `prod-analytics-stream-page_views` |
| Meta table | `{base}-meta` | `prod-analytics-meta` |
| View table, one per version | `{base}-view-{view}-v{N}` | `prod-analytics-view-page_daily-v2` |
| S3 bucket | `{base}-{account}-{region}-an` | `prod-analytics-123456789012-us-east-1-an` |
| Projector function | `{base}-projector`, or `{base}-projector-{stream}` with `runtime.split: stream` | `prod-analytics-projector` |
| Setup function | `{base}-setup` | `prod-analytics-setup` |
| Function log group | `/aws/lambda/{function}` | `/aws/lambda/prod-analytics-setup` |
| Glue database | `{base}` with every `-` replaced by `_` | `prod_analytics` |
| Athena workgroup | `{base}` | `prod-analytics` |
| Iceberg table | `{stream}` | `page_views` |
| Athena view, one row per event | `{stream}_dedup` | `page_views_dedup` |
| Firehose stream | `{base}-archive-{stream}` | `prod-analytics-archive-page_views` |
| Firehose log group | `/aws/kinesisfirehose/{base}-archive`, with one log stream `{stream}` per Firehose stream | `/aws/kinesisfirehose/prod-analytics-archive` |
| Alarms | `{resource name}-{signal}` or `{base}-{signal}` ([§10](#10-alarms-and-dashboard)) | `prod-analytics-projector-lag` |
| Dashboard | `{base}-{region}` | `prod-analytics-us-east-1` |
| IAM roles | Chosen by CloudFormation | |

- `regional.yaml` is deployed in every region of one account, so a name that AWS requires
  to be unique in the account includes the region (the dashboard) or is left to
  CloudFormation (the roles). Unnamed roles also mean a deploy needs `CAPABILITY_IAM`, not
  `CAPABILITY_NAMED_IAM`.
- The bucket is in the S3 account regional namespace: only this account can create a name
  that ends in `-{account}-{region}-an`, so no one else can take it first. `me-south-1` and
  `me-central-1` don't offer that namespace, so Dynaflux doesn't support them (DF6104).
- `validate` doesn't check the alarm names; `generate` fails if one would be too long. The
  dashboard and log group names always fit once the function names do.

**Tags.** Every resource that CloudFormation can tag, except the event source mappings,
carries these tags:

| Tag | Value |
|-----|-------|
| `dynaflux:store` | The store. |
| `dynaflux:kind` | `stream`, `view`, `meta`, `projector`, `setup`, `archive` or `bucket`. |
| `dynaflux:name` | The stream or view the resource belongs to, if any. |
| `dynaflux:version` | View tables only: the version number. |
| `dynaflux:fingerprint` | View tables only: the version's fingerprint in `dynaflux.lock`. `generate` reads it back ([§13](#13-checks-in-generate)). |

Both view tags are fixed for a version, so they never cause an update. No tag holds the
Dynaflux release: such a tag would update every resource on every upgrade.

**Logical IDs** are a kind word followed by the name in PascalCase: `StreamPageViews`,
`ViewPageDailyV2`, `MappingPageViews`, `FirehosePageViews`, `LogsProjector`, `RoleSetup`.
Two names have the same PascalCase form when a `_` isn't followed by a letter (`a_1` and
`a1`), so such a name also gets `X` and the first 8 hex digits of its SHA-256: `a_1`
becomes `A1X` and 8 digits. A logical ID depends on the name alone, never on
`runtime.split` or another setting, and it never changes for the life of a store:
CloudFormation treats a new logical ID as a new resource, which fails for a named resource
and replaces any other.

## 4. `global.yaml`

One `AWS::DynamoDB::GlobalTable` per stream, `Stream<Name>`:

| Setting | Value | Why |
|---------|-------|-----|
| Keys | `pk` and `sk`, both strings; no indexes | [encoding.md §2](encoding.md#2-tables-and-items) |
| Capacity | `PAY_PER_REQUEST`, or `PROVISIONED` with auto scaling from `tables.<stream>` or `defaults`: one write policy for the table and a read policy per replica, with `SeedCapacity` at `min` | [config.md](config.md#tables). The billing mode is always written, because CloudFormation's default is provisioned. `SeedCapacity` lets the table switch modes. |
| Consistency | `MultiRegionConsistency: EVENTUAL` | It can't change after creation. |
| Stream | `NEW_AND_OLD_IMAGES` | The projector compares both images of a `MODIFY`. The view type can't change once a table has two replicas. |
| Time to live | On, attribute `_ttl` | Events expire after the stream's `LOG RETENTION` ([encoding.md §5.4](encoding.md#54-_ttl)). It is on even for `LOG RETENTION FOREVER`, whose events have no `_ttl`: DynamoDB allows one TTL change per hour, so turning it on and off would make a quick redeploy or a rollback fail. |
| Replicas | One per region in `regions` | |
| Deletion protection | On for every replica, except the region named by `generate --unprotect-region` ([§13](#13-checks-in-generate)) | It protects the facts. It is set per replica, because DynamoDB doesn't copy it between replicas. |
| Point-in-time recovery | On for every replica | The stream tables hold the facts, and with a short log it costs little. |
| Deletion and replacement | `Retain` | Facts outlive the stack. Not `RetainExceptOnCreate`: deletion protection would make a create rollback fail anyway. |
| Encryption | AWS owned key, the default | [§14](#14-deliberate-omissions) |

The templates set no table class, Kinesis streaming, contributor insights, witnesses or
resource policy. Tools such as AWS FIS add statements to a table's resource policy, and a
stack that managed the policy would remove them.

**Stack policy.** `global.stack-policy.json` allows every update except replacing a stream
table (`Update:Replace`). A replaced stream table starts empty while the retained old one
keeps the facts, and writers and projectors can end up on different tables; `Retain` alone
doesn't prevent that. The policy names the resource type, `AWS::DynamoDB::GlobalTable`,
rather than the tables, so the stream tables added after it was set are protected too, and
it is set once. Removing a stream (`Update:Delete`) stays allowed, since its table is
retained. `regional.yaml` has no stack policy: a prefix or store change there already fails
([§12](#12-changes-after-the-first-deploy)), and a stack policy would rule out CloudFormation
stack refactoring, one way to split `regional.yaml` if a store outgrows it
([§15](#15-not-in-these-templates-yet)).

## 5. Storage

### 5.1 Meta and view tables

`regional.yaml` holds an `AWS::DynamoDB::Table` for the meta table, `Meta`, and one for each
view version that `dynaflux.lock` lists as current or retained, `View<Name>V<N>`.

| Setting | Value | Why |
|---------|-------|-----|
| Keys | `pk` and `sk`, both strings | [encoding.md §2](encoding.md#2-tables-and-items) |
| Capacity | `defaults` for the meta table; `tables.<view>` or `defaults` for every table of a view | [config.md](config.md#tables) |
| Time to live | On, attribute `_ttl` | View rows of views with `TTL`, and meta items, expire ([encoding.md §7.7](encoding.md#77-expiry), [§8.1](encoding.md#81-unit-item)). |
| Deletion protection | Off | `dynaflux retire` (M5) deletes a retired version's table. |
| Point-in-time recovery | Off | [§14](#14-deliberate-omissions) |
| Deletion and replacement | `Delete` | See below. |

The meta and view tables are derived state that lives and dies together. A meta table that
outlived its view tables would mark new, empty view tables `live` and skip every record
before its saved progress, so the views would be wrong without any error. Deleting the stack
deletes them all, and a backfill from the archive (M5) rebuilds them.

A provisioned table starts at the `min` capacity and scales with Application Auto Scaling
target tracking at `target_percent`, through `ReadTarget<ID>`, `ReadPolicy<ID>`,
`WriteTarget<ID>` and `WritePolicy<ID>`, where `<ID>` is the table's logical ID. The
targets use the service-linked role, so the template creates no role for them.

### 5.2 Bucket

`Bucket` (`AWS::S3::Bucket`) exists in every region, even where nothing is archived: the
event source mappings write what they discard to it.

| Setting | Value |
|---------|-------|
| Namespace | `account-regional` ([§3](#3-names-tags-and-logical-ids)) |
| Public access | All four blocks on |
| Object ownership | `BucketOwnerEnforced`: no ACLs |
| Encryption | SSE-S3 (`AES256`) |
| Versioning | On |
| Lifecycle | Abort incomplete multipart uploads after 7 days. Delete noncurrent versions after 30 days, and remove expired delete markers. Nothing expires current objects. |
| Bucket policy | Deny every request made without TLS (`aws:SecureTransport` is `false`). |
| Deletion and replacement | `RetainExceptOnCreate`; `Retain` on replacement |

- **Versioning:** the archive is the only copy of events older than a stream's log window.
  The table optimizers rewrite and delete files, and versioning keeps deleted files for 30
  days. Leftover delete markers would slow every listing of `warehouse/`, so the lifecycle
  rule removes them.
- **Deletion:** the bucket stays when the stack is deleted, and goes when the create that
  made it rolls back, so a failed first deploy can be retried as it is. S3 refuses to
  delete a bucket that holds objects, so this can't destroy data.

| Key prefix | Written by | Holds |
|------------|------------|-------|
| `warehouse/<database>/<stream>/iceberg/` | Firehose, the setup function, the table optimizers | One Iceberg table per archived stream ([§7.3](#73-tables-and-columns)). |
| `errors/firehose/<stream>/` | Firehose | Records that Firehose couldn't deliver. |
| `aws/lambda/<mapping UUID>/<shard ID>/YYYY/MM/DD/…` | Lambda | What an event source mapping discarded. Lambda chooses this key. |

## 6. Functions and event source mappings

### 6.1 Functions

`regional.yaml` has a projector function, `Projector` (`runtime.split: store`) or one
`Projector<Stream>` per stream (`split: stream`), and the setup function, `Setup`. Each
function has its own log group, `Logs<ID>`, and role, `Role<ID>` ([§9](#9-iam)).

| Setting | Value |
|---------|-------|
| Type | `AWS::Serverless::Function` |
| Code | `CodeUri` is `runtime.out` relative to `infra.out`: `../../cmd/dynaflux-runtime` with the defaults. `Metadata` is `{BuildMethod: go1.x}`. |
| Runtime, handler | `provided.al2023`, `bootstrap` |
| Architecture, memory | `runtime.arch`, `runtime.memory_mb` |
| Timeout | Projectors: `runtime.timeout_seconds`. Setup: 900 seconds. |
| Environment | `DYNAFLUX_MODE` (`projector` or `setup`), `DYNAFLUX_STORE`, and `DYNAFLUX_PREFIX` (the `Prefix` parameter). Projectors in archive regions also get `DYNAFLUX_ARCHIVE_SCHEMA` ([§7.2](#72-archive-schema)). |
| Logs | JSON, to the function's log group, kept 30 days |

- Every function has the same `Metadata`, with nothing else in it: SAM CLI builds functions
  together only when their metadata is equal, so `sam build` compiles the binary once.
- The setup function ignores `runtime.timeout_seconds`. That setting is bound by
  `runtime.prune_window_seconds` (DF6305) because projectors write view rows; the setup
  function never does, and its Athena queries can take minutes.

### 6.2 Stream ARN lookup

An event source mapping needs the exact ARN of the local replica's stream, and a regional
stack can't get it from CloudFormation: a Global Table returns its stream ARN only in the
region of the stack that owns it, and the ARN ends in a label chosen when the stream was
created. So `regional.yaml` has one `Lookup<Stream>` per stream, a
`Custom::DynafluxStreamArn` custom resource that the setup function serves:

- It describes the stream table in the stack's region and returns its stream ARN.
- It accepts a table that is `ACTIVE` or `UPDATING` when the stream exists and the local
  replica is `ACTIVE`.
- It fails the deploy, with the reason, when the table or the local replica doesn't exist
  ("deploy `global.yaml` first, with the same `Prefix`"), when the replica isn't `ACTIVE`,
  or when the stream view isn't `NEW_AND_OLD_IMAGES`. So deploying `regional.yaml` before
  `global.yaml`, or in a region outside `regions`, fails here, and the rollback leaves
  nothing behind.
- It retries `AccessDenied` for about 60 seconds, while new permissions take effect. It
  times out after 300 seconds.
- CloudFormation calls it again only when its properties change. If a stream table or a
  replica is re-created by hand, deploy that region's regional stack with a new
  `LookupGeneration`, such as `2`: every lookup runs again, and the mapping of a stream
  whose ARN changed is replaced by one on the new stream, which starts at its oldest
  record. The meta and view tables stay as they are.

### 6.3 Event source mappings

`Mapping<Stream>` (`AWS::Lambda::EventSourceMapping`), one per stream, connects the local
replica's stream to its projector. Its settings are the fixed values of
[§8](#8-fixed-values), plus:

| Setting | Value |
|---------|-------|
| `FunctionName` | The projector; with `split: stream`, the stream's own projector. A change of `split` updates the mapping in place. |
| `EventSourceArn` | The ARN that `Lookup<Stream>` returns. |
| `MaximumBatchingWindowInSeconds` | `runtime.batching_window_seconds` |
| `DestinationConfig.OnFailure` | The bucket. |
| `FilterCriteria` | None. A filter can't be combined with a tumbling window ([ADR 0003](../decisions/0003-shard-identity-from-tumbling-window.md)), so the projector skips `REMOVE` records itself. |

The logical ID, the source ARN and the starting position depend only on the stream's name
and table, so no ordinary change replaces a mapping. A replacement would briefly put a
second reader on the stream.

## 7. Archive

`regional.yaml` has the archive resources when at least one stream is archived
([config.md](config.md#archive)). When `archive.regions` lists only some of `regions`, the
template gets a `RegionSets` mapping, with `Archive` set to `"true"` or `"false"` for each
region, and a condition `InArchive`. Every archive resource then carries
`Condition: InArchive`, and references to archive resources from other resources (an IAM
statement, an environment variable) use `Fn::If`, so one template serves every region.

`archive.streams.<stream>.enabled: false` removes that stream's Firehose stream and its entry
in `ArchiveSchema`. Its Iceberg table, data and optimizers stay.

### 7.1 Resources

| Logical ID | Type | Settings |
|------------|------|----------|
| `ArchiveWorkGroup` | `AWS::Athena::WorkGroup` | Engine version 3, managed query results, configuration enforced. `RecursiveDeleteOption: true`: Athena refuses to delete a workgroup that has run any query otherwise, and the setup function runs queries in it on every deploy. Deleting it deletes its query history and saved queries, so don't save queries you want to keep in it. |
| `ArchiveSchema` | `Custom::DynafluxArchiveSchema` | The Glue database, the Iceberg tables and their optimizers ([§7.2](#72-archive-schema)). `Retain`. |
| `Firehose<Stream>` | `AWS::KinesisFirehose::DeliveryStream` | [§7.4](#74-firehose-streams) |
| `LogsArchive`, `LogStream<Stream>` | `AWS::Logs::LogGroup`, `AWS::Logs::LogStream` | Firehose's log group, kept 30 days, with one log stream per Firehose stream. |
| `RoleArchive` | `AWS::IAM::Role` | Firehose's role ([§9.3](#93-firehose-role)). |
| `RoleArchiveOptimizer` | `AWS::IAM::Role` | The table optimizers' role ([§9.4](#94-optimizer-role)). |

### 7.2 Archive schema

The Glue database and the Iceberg tables aren't CloudFormation resources. `ArchiveSchema`
holds their desired state as properties, and the setup function applies it with the Glue
API and Athena DDL ([ADR 0008](../decisions/0008-archive-schema-migration.md)):

- **Properties:** the database and its location, `s3://<bucket>/warehouse/<database>/`, the
  workgroup, the optimizer role and settings, and for each archived stream its table:
  location and columns in order. Each column has its name, its type and, if it has one, its
  `DEFAULT` as an Athena literal, from which the function writes the dedup view.
  `Fingerprint` is a SHA-256 of the tables that doesn't depend on the prefix. A change set
  shows a schema change as a change of these properties.
- **Create and update:** the function creates the database if it is missing. For each
  table, it creates the table if it is missing (Iceberg v2, Parquet, zstd, partitioned by
  `day(event_time)`), and otherwise adds the missing columns. It fails rather than move a
  table, change its partitioning or change a column's type, and it never drops anything: a
  column that the table has and the properties lack stays. Then it creates or updates each
  table's compaction and snapshot-retention optimizers, and re-creates each
  `<stream>_dedup` view. Each call retries `AccessDenied` for about 60 seconds, while the
  permissions and the optimizer role that the same deploy creates take effect. It times out
  after 900 seconds.
- **Delete:** does nothing. The database, the tables and their optimizers outlive the
  stack, so a new regional stack, or an archive turned back on, finds them and goes on
  with them.
- **Order:** `ArchiveSchema` waits for every stream lookup, so a missing replica fails the
  deploy before any table is written, and every Firehose stream waits for `ArchiveSchema`.
  Each projector's `DYNAFLUX_ARCHIVE_SCHEMA` is the fingerprint, so CloudFormation updates
  the projectors after the schema, and changes their configuration exactly when the schema
  changes.
- **Guard:** Firehose silently skips fields its table lacks, so this order matters. The
  projector compares `DYNAFLUX_ARCHIVE_SCHEMA` with the fingerprint that its own catalog
  gives for its region. It fails the whole batch when they differ, when the variable is
  missing in a region its catalog archives in, or when it is set in a region that doesn't
  archive. The shard waits, the lag alarms fire, and no column is lost silently, even when
  a function is updated outside CloudFormation.

A deploy that changes the schema briefly fails projector batches while CloudFormation
updates a function's configuration and its code in two steps. The batches retry, and the
errors alarm needs three periods to fire.

The database isn't an `AWS::Glue::Database` resource: a retained one would make re-creating
the regional stack, or turning the archive back on, fail with `AlreadyExists`, and one
deleted with the stack would take the tables' entries with it.

The optimizers aren't `AWS::Glue::TableOptimizer` resources: that type exists in only 15
regions, and CloudFormation checks a template's resource types before its conditions, so one
such resource would fail `regional.yaml` in every other region, archiving or not. As a
result, an optimizer deleted by hand comes back only at the next change to `ArchiveSchema`'s
properties.

### 7.3 Tables and columns

- **Location:** `s3://<bucket>/warehouse/<database>/<stream>/iceberg/`. The final
  `iceberg/` keeps one table's location from being a key prefix of another's (`page` and
  `page_views`): tools that remove orphan files can delete files under an overlapping
  location.
- **Columns:** the implicit columns, the declared columns in declaration order, then
  `_shard`, `_seq` and `_arrival`. Every column is optional (nullable): Iceberg v2 can add
  only optional columns, and then a missing value is never a delivery error.
- **Partitioning:** by `day(event_time)`.
- **Names** are quoted in every generated statement, so columns named like Athena reserved
  words, such as `date`, and columns that start with `_` work.

| Dynaflux type | Column type |
|---------------|-------------|
| `String`, `LowCardinality(String)`, `UUID` | `string` |
| `UInt8`, `UInt16`, `Int8`, `Int16`, `Int32` | `int` |
| `UInt32`, `Int64` | `bigint` |
| `UInt64` | `decimal(20,0)`, because a `bigint` can't hold 2^64 − 1 |
| `Float64` | `double` |
| `Decimal(P, S)` | `decimal(P,S)` |
| `Bool` | `boolean` |
| `Date` | `date` |
| `DateTime64(3)`, `DateTime64(6)` | `timestamp` (microseconds, UTC) |
| `Array(T)` | `array<T'>`, where `T'` is the column type of `T` |
| `Nullable(T)` | The column type of `T` |

| Column | Type | Value |
|--------|------|-------|
| `_shard` | `string` | The DynamoDB stream shard the record came from. |
| `_seq` | `string` | The record's sequence number, zero-padded to 40 digits so that string order is numeric order. |
| `_arrival` | `timestamp` | When the record entered the stream, rounded down to the second by DynamoDB. |

The archive is at least once: a retried batch can archive an event twice. The view
`<stream>_dedup` keeps one row per event, and reads rows archived before a column existed
with that column's `DEFAULT`, or `NULL` for a `Nullable` column. Filter it on `event_time`
to limit the days Athena reads ([§16](#16-to-be-confirmed-on-aws)).

### 7.4 Firehose streams

`Firehose<Stream>`, one per archived stream:

| Setting | Value | Why |
|---------|-------|-----|
| Type | Direct PUT | The projector sends the records. |
| Destination | Apache Iceberg Tables in this account's Glue Data Catalog in this region: table `<stream>` in the archive database | Each Iceberg table has one writer. |
| `AppendOnly` | `true` | Firehose accepts it only at creation. It also lifts the 1 MiB/s Direct PUT limit that applies outside us-east-1, us-west-2 and eu-west-1. |
| Buffering | 300 seconds or 128 MiB, whichever comes first | Each flush commits an Iceberg snapshot. Firehose's 5 MiB default would commit one every few seconds under steady load. |
| Retries | 7,200 seconds | Keeps records out of the error prefix through longer outages. |
| Backup | Failed records only, under `errors/firehose/<stream>/` | |
| Logs | `LogsArchive`, log stream `<stream>` | |

Dynaflux creates and evolves the tables itself, so Firehose's schema evolution and automatic
table creation stay off, and so do record processors. The name, the type, `AppendOnly` and
the catalog are constants or derive from the stream name, so no configuration change can
alter them: a replaced Firehose stream would drop its buffer.

Deleting a Firehose stream can lose the records it still buffers;
[§12](#12-changes-after-the-first-deploy) says how to stop archiving a stream.

## 8. Fixed values

These values are constants of Dynaflux, not configuration keys. Changing one takes a design
change and a new Dynaflux release.

| Value | Setting | Why |
|-------|---------|-----|
| Starting position | `TRIM_HORIZON` | `LATEST` can miss records while a mapping is created or updated. |
| Batch size | 100 | Lambda's default. The batching window (`runtime.batching_window_seconds`), not the size, controls cost; `dynaflux explain` assumes 100. |
| Parallelization factor | 1 | The projector applies each shard in order, one batch at a time. |
| Bisect batch on error | On | It isolates a failing record, and splitting doesn't use up retries. |
| Function response types | `ReportBatchItemFailures` | Retries resume at the failed record ([ADR 0003](../decisions/0003-shard-identity-from-tumbling-window.md)). |
| Maximum retry attempts | -1 (unlimited) | A discarded batch would leave a hole that the view rows' high-water marks can't represent, so failures retry until the stream trims the records after 24 hours. |
| Maximum record age | -1 (unlimited) | Lambda never discards a record it can still read. A finite age would also discard records that are merely old when a mapping is created, for example after a regional deploy that lags a new stream by a day. |
| Tumbling window | 900 seconds | It only tells the projector its shard ([ADR 0003](../decisions/0003-shard-identity-from-tumbling-window.md)). |
| Mapping metrics | `EventCount` | Per-mapping counts for the discarded and polling alarms ([§10](#10-alarms-and-dashboard)). |
| Log retention | 30 days | Long enough to investigate an incident; logs aren't the record. |
| Firehose buffering and retries | 300 seconds or 128 MiB; 7,200 seconds | [§7.4](#74-firehose-streams) |
| Table optimizers | Compaction (`binpack`); snapshots kept 5 days, at least 1, with expired files removed | Firehose commits small files and one snapshot per flush. Orphan-file removal waits until a store needs it. |
| Setup timeout | 900 seconds | [§6.1](#61-functions) |
| Alarms | [§10](#10-alarms-and-dashboard) | |

## 9. IAM

- One role per function, plus a role for Firehose and one for the table optimizers. Roles
  have no names ([§3](#3-names-tags-and-logical-ids)).
- Permissions are inline policies, so they exist before CloudFormation creates a mapping
  that needs them. No AWS managed policies.
- Resources are exact ARNs, taken from the resources themselves. `*` appears only for
  `dynamodb:ListStreams`, which has no resource type. There are no wildcard ARNs such as
  `table/{base}-view-*`: one would also match the tables of another store named
  `{store}-view-…`.
- Statements about archive resources exist only in archive regions.
- No role can call `dynamodb:DeleteItem`, `UpdateItem` or the transaction actions: the
  runtime always writes whole items
  ([ADR 0004](../decisions/0004-runtime-storage-boundary.md)).
- Functions publish metrics in CloudWatch embedded metric format logs, so no role needs
  `cloudwatch:PutMetricData`.
- A trust policy names the service, with a condition only where the service documents one:
  `sts:ExternalId` for Firehose.

### 9.1 Projector role

Trusts `lambda.amazonaws.com`. With `split: stream`, each projector's role covers only its
stream, that stream's Firehose stream, and the views that read the stream.

| Statement | Actions | Resources |
|-----------|---------|-----------|
| `Logs` | `logs:CreateLogStream`, `logs:PutLogEvents` | The function's log group |
| `ReadStreams` | `dynamodb:DescribeStream`, `GetRecords`, `GetShardIterator` | The streams of its stream tables (`<table ARN>/stream/*`) |
| `ListStreams` | `dynamodb:ListStreams` | `*` |
| `Meta` | `dynamodb:BatchGetItem`, `GetItem`, `PutItem`, `Query` | The meta table |
| `Views` | `dynamodb:BatchGetItem`, `GetItem`, `PutItem` | The table of every current and retained version of the views that read its streams |
| `Archive` | `firehose:PutRecordBatch` | The Firehose streams of its archived streams |
| `FailureList` | `s3:ListBucket` | The bucket, when `s3:ResourceAccount` is this account |
| `FailurePut` | `s3:PutObject` | `aws/lambda/*` in the bucket, with the same condition |

The `Views` statement refers to each view table, so CloudFormation creates a new view table
before it updates the code that writes to it. Lambda uses the `Failure*` statements to write
discarded records to the bucket on the mapping's behalf.

### 9.2 Setup role

Trusts `lambda.amazonaws.com`. The statements whose names start with `Archive` exist only in
archive regions.

| Statement | Actions | Resources | Condition |
|-----------|---------|-----------|-----------|
| `Logs` | `logs:CreateLogStream`, `logs:PutLogEvents` | The function's log group | |
| `StreamTables` | `dynamodb:DescribeTable` | The stream tables in this region | |
| `ArchiveQueries` | `athena:GetQueryExecution`, `GetQueryResults`, `StartQueryExecution`, `StopQueryExecution` | The workgroup | |
| `ArchiveAthenaCatalog` | `glue:CreateDatabase`, `GetDatabase`, `GetDatabases` | The Glue catalog and `database/default`, which Athena needs in every region | |
| `ArchiveCatalog` | `glue:CreateDatabase`, `CreateTable`, `CreateTableOptimizer`, `GetDatabase`, `GetDatabases`, `GetPartitions`, `GetTable`, `GetTableOptimizer`, `GetTables`, `UpdateTable`, `UpdateTableOptimizer` | The Glue catalog, the archive database and its tables | |
| `ArchivePassOptimizerRole` | `iam:PassRole` | The optimizer role | `iam:PassedToService` is `glue.amazonaws.com` |
| `ArchiveFiles` | `s3:GetObject`, `s3:PutObject` | `warehouse/<database>/*` in the bucket | |
| `ArchiveList` | `s3:ListBucket` | The bucket | `s3:prefix` is `warehouse/<database>` or starts with `warehouse/<database>/` |
| `ArchiveBucketLocation` | `s3:GetBucketLocation` | The bucket | None: the request has no prefix |

There is no `s3:DeleteObject`: creating a table, adding columns and replacing a view delete
no files, and only the optimizers should delete archive files.

### 9.3 Firehose role

Trusts `firehose.amazonaws.com` when `sts:ExternalId` is this account.

| Statement | Actions | Resources |
|-----------|---------|-----------|
| `Catalog` | `glue:GetDatabase`, `GetTable`, `UpdateTable` | The Glue catalog, the archive database and all its tables |
| `Files` | `s3:AbortMultipartUpload`, `DeleteObject`, `GetObject`, `PutObject` | `warehouse/<database>/*` and `errors/firehose/*` in the bucket |
| `Bucket` | `s3:GetBucketLocation`, `ListBucket`, `ListBucketMultipartUploads` | The bucket |
| `Logs` | `logs:PutLogEvents` | Firehose's log group |

- One role serves every Firehose stream in the region. It covers all of the database's
  tables, so the policy doesn't grow with the streams, and a Firehose stream that still
  delivers after its table's entry is gone keeps working.
- `s3:DeleteObject` is granted as in AWS's Firehose-to-Iceberg example: without it, a
  failure would show only as `S3.AccessDenied` records under `errors/`. Bucket versioning
  keeps deleted files for 30 days. The grant goes if the end-to-end suite shows that
  Firehose never uses it.
- There is no `glue:Create*`: Dynaflux creates the tables.

### 9.4 Optimizer role

Trusts `glue.amazonaws.com`.

| Statement | Actions | Resources |
|-----------|---------|-----------|
| `Files` | `s3:DeleteObject`, `GetObject`, `PutObject` | `warehouse/<database>/*` in the bucket |
| `List` | `s3:ListBucket`, when `s3:prefix` is `warehouse/<database>` or starts with `warehouse/<database>/` | The bucket |
| `Catalog` | `glue:GetTable`, `UpdateTable` | The Glue catalog, the archive database and its tables |
| `Logs` | `logs:CreateLogGroup`, `CreateLogStream`, `PutLogEvents` | The log groups `/aws-glue/iceberg-compaction/logs` and `/aws-glue/iceberg-retention/logs` |

Glue creates those two log groups itself, without a retention, and every store in the
account and region shares them, so no stack owns them. Set their retention once per account
and region ([§11](#11-deploying)).

### 9.5 Policy size

IAM allows 10,240 characters, not counting whitespace, for all the inline policies of one
role. `generate` measures each role as it would be with the longest prefix that `Prefix`
accepts, the longest region in `regions`, a 12-digit account ID and the longest partition
name, and fails if a role is over the limit. A projector role grows with its streams,
Firehose streams and view versions: with `split: store`, 25 streams and 60 view versions
come to about 11,600 characters. The error names the role and its size, and suggests
`split: stream`, which gives each stream's projector its own role, or retiring old view
versions (M5).

## 10. Alarms and dashboard

`generate` fixes the alarms and their thresholds; add your own alarms for anything else.
Every alarm:

- is named after the resource it watches and its signal, or after the store for store-wide
  alarms;
- has a description that starts with `critical:` or `warning:` and says what to do;
- notifies `AlarmTopicArn` when it is set ([§2](#2-parameters));
- states how it treats missing data: as not breaching, unless the table says otherwise;
- uses plain metrics or metric math, never a Metrics Insights query. CloudWatch allows 200
  Metrics Insights alarms per account and region, a limit that can't be raised and that
  every application in the account shares.

Periods are 5 minutes. `{projector}` is the projector function's name, and `{base}` is
`{prefix}{store}`.

| Alarm | Metric | Fires when | Severity |
|-------|--------|------------|----------|
| `{projector}-lag` | `AWS/Lambda` `IteratorAge`, maximum | ≥ 15 minutes for 3 periods | warning |
| `{projector}-gap-risk` | The same | ≥ 6 hours for 1 period. Records are trimmed after 24 hours. | critical |
| `{projector}-errors` | `AWS/Lambda` `Errors`, sum | ≥ 1 for 3 periods. A deploy that changes the archive schema causes brief failures ([§7.2](#72-archive-schema)). | warning |
| `{projector}-throttles` | `AWS/Lambda` `Throttles`, sum | ≥ 1 for 3 periods | warning |
| `{base}-projector-{stream}-discarded` | `OnFailureDestinationDeliveredEventCount` plus `DroppedEventCount` of the stream's mapping, sum | ≥ 1 in 1 period. The mapping sent records to its on-failure destination, under `aws/lambda/` in the bucket. With unlimited retries and record age, neither metric counts records that the stream trims after 24 hours: `gap-risk` warns before that ([§16](#16-to-be-confirmed-on-aws)). | critical |
| `{base}-projector-{stream}-polling` | `PolledEventCount` of the stream's mapping, sample count | < 1 for 3 periods, and missing data breaches: the mapping is disabled or has lost its permissions. | critical |
| `{stream table}-write-throttles` | `AWS/DynamoDB` `WriteThrottleEvents` of the local replica, sum | ≥ 1 for 3 periods | warning |
| `{base}-views-broken` | `Dynaflux` `BreakerOpened`, sum | ≥ 1 in 1 period. A view stopped at an event it can't apply. | critical |
| `{base}-rows-too-large` | `Dynaflux` `RowTooLarge`, sum | ≥ 1 in 1 period. A view row passed DynamoDB's 400 KB item limit ([encoding.md §7.8](encoding.md#78-size-bound)). | critical |
| `{Firehose stream}-freshness` | `AWS/Firehose` `DeliveryToIceberg.DataFreshness`, maximum | ≥ 15 minutes for 3 periods | warning |
| `{Firehose stream}-failed-rows` | `AWS/Firehose` `DeliveryToIceberg.FailedRowCount`, sum | ≥ 1 in 1 period. Records went to `errors/firehose/` in the bucket. | critical |

Each region has 4 alarms per projector function, 3 per stream, 2 for the store, and 2 per
archived stream where it is archived: 11 for a store with one archived stream and
`split: store`. The `Dynaflux` metrics come from the runtime, in the namespace `Dynaflux`
with the dimension `Store`.

**Dashboard.** `Dashboard` is named `{base}-{region}`, because dashboard names are
account-wide. It shows the alarm states; the projectors' iterator age, invocations, errors
and throttles; the archive's incoming and delivered records and its data freshness; consumed
write capacity and throttles per table; replication latency from each other region; DynamoDB
system errors; and the runtime's opened breakers, too-large rows and divergent duplicates
(one dedup key written with different payloads, [encoding.md §6](encoding.md#6-stream-items)).
Replication latency, view and meta table throttles, system errors, divergent duplicates and
Firehose throttling have no alarm. The per-table widgets search by the store's name prefix,
so new view versions appear without a change to the template.

## 11. Deploying

**Before the first deploy:**

- Lake Formation must leave plain IAM access to the Glue Data Catalog in place, which is the
  default (`IAMAllowedPrincipals` keeps its permissions). The archive uses IAM only.
- Choose the home region for `global.yaml`, one of `regions`. It can't move later.

**Build** the runtime binary once, from the project root, after `dynaflux generate`:

```sh
export CGO_ENABLED=0 GOFLAGS=-tags=lambda.norpc
sam build -t infra/dynaflux/regional.yaml
```

AWS recommends both settings for Go on `provided.al2023`, and SAM's Go builder sets neither.
Build and deploy from the tree that `generate` wrote, so that the binary and the templates
agree.

**Deploy** `global.yaml` in the home region, then `regional.yaml` in every region of
`regions`. With `prefix: prod-`, `store: analytics` and the home region `us-east-1`:

```sh
sam deploy -t infra/dynaflux/global.yaml --stack-name prod-analytics-global \
  --region us-east-1 --resolve-s3 --parameter-overrides Prefix=prod-

# First deploy only:
aws cloudformation set-stack-policy --stack-name prod-analytics-global --region us-east-1 \
  --stack-policy-body file://infra/dynaflux/global.stack-policy.json

# In every region of regions:
sam deploy --stack-name prod-analytics-regional --region us-east-1 \
  --capabilities CAPABILITY_IAM CAPABILITY_AUTO_EXPAND --resolve-s3 \
  --parameter-overrides Prefix=prod-
```

- `sam deploy` without `-t` deploys the template that `sam build` wrote, so every region
  gets the same binary.
- `--resolve-s3` uploads the template to an S3 bucket that SAM manages. CloudFormation
  takes at most 51,200 bytes inline, which `global.yaml` passes at about 30 streams in
  three regions.
- For alarm notifications, add `AlarmTopicArn=<topic ARN>` to `--parameter-overrides`, with
  a topic in that region.
- Stack names are a suggestion: Dynaflux finds resources by name, not by stack.

**After the table optimizers first run,** set a retention on the two log groups that Glue
creates for them, once per account and region ([§9.4](#94-optimizer-role)):

```sh
aws logs put-retention-policy --log-group-name /aws-glue/iceberg-compaction/logs --retention-in-days 30
aws logs put-retention-policy --log-group-name /aws-glue/iceberg-retention/logs --retention-in-days 30
```

## 12. Changes after the first deploy

After any change to the SQL files or `dynaflux.yaml`, run `dynaflux generate`, rebuild, and
deploy the templates that changed: `global.yaml` first, then `regional.yaml` in every
region.

| Change | What happens, and what to do |
|--------|------------------------------|
| New column | Deploy `regional.yaml` in every region. `ArchiveSchema` adds the column to the archive table before CloudFormation updates the projector. |
| New view version | Deploy `regional.yaml` in every region. The new table exists before the code that writes it. |
| New stream | Deploy `global.yaml` (a new table, with every replica), then `regional.yaml` in every region (its lookup, mapping and archive table). Deploy the regional stacks before the application writes to the stream, and within hours: a stream keeps records for 24 hours, and a mapping created later misses older ones. |
| Retire a view version (M5) | Deploy `regional.yaml`. CloudFormation deletes the version's table at the end of the update. |
| Change `runtime.split` | Deploy `regional.yaml`. Functions are created and deleted, and the mappings are updated in place. |
| Change capacity | Deploy the template that holds the table. DynamoDB lets a table switch from provisioned to on-demand at most 4 times in 24 hours. |
| Add a region | One region per change (`generate` refuses more, DF6017), and nothing else in the same deploy. Add it to `regions`, run `generate`, and deploy `global.yaml`: DynamoDB copies the existing items to the new replica, which can take hours. Then deploy `regional.yaml` in the new region. Its view versions start empty and need a backfill (M5). |
| Remove a region | Never the home region. Delete the region's regional stack. Run `generate --unprotect-region <region>` and deploy `global.yaml`, which turns off deletion protection on that region's replicas; `generate` refuses to remove the region before that (DF6018). Then remove the region from `regions`, run `generate`, and deploy `global.yaml`: DynamoDB deletes the region's replicas, with their data. The region's bucket and Glue database stay. |
| Stop archiving a stream: `enabled: false`, a dropped stream, or a shorter `archive.regions` | CloudFormation deletes the Firehose stream, and Firehose doesn't promise to deliver the records it still buffers (up to 300 seconds or 128 MiB), although the projector counted them as sent. To drop a stream: stop writing to it, wait until the projector's iterator age is near 0 and the archive's data freshness has drained, then deploy. For a stream that stays, the archive may miss up to one buffer before the change; when only `archive.regions` shrinks, the other regions' archives keep their copies. The Glue database, the Iceberg tables and their files stay, and archiving again goes on with them. |
| Drop a stream | Its Global Table, Iceberg table and archive files stay; its mapping, lookup and Firehose stream go. Delete what stays by hand. |
| Change `prefix` or `store` | Deploy new stacks. Updating an existing stack fails: the setup function's ARN changes, and a custom resource's service token can't. The stack policy also refuses to replace stream tables. |

To recover from a failed or lost stack:

| Situation | What to do |
|-----------|------------|
| A first `global.yaml` deploy failed part-way | The tables it created stay. Delete them by hand, turning off deletion protection first, or adopt them into the stack with a change set that imports existing resources (`--import-existing-resources`). |
| A first `regional.yaml` deploy failed after the bucket received objects | S3 won't delete a bucket that isn't empty, so the rollback ends in `ROLLBACK_FAILED`. Delete the stack and keep `Bucket` (`--retain-resources Bucket`), then import the bucket into the next stack (`--import-existing-resources`). The archive's Glue database and tables stay too, and the next deploy goes on with them. |
| A regional stack was deleted | Its bucket stays, with the archive: the only copy of events older than the log window. Import it when you create the new stack (`--import-existing-resources`), and never delete it to make way. The Glue database and tables stay too, and the new stack's `ArchiveSchema` goes on with them. The meta and view tables were deleted with the stack, and need a backfill (M5). |
| A stream table or a replica was re-created by hand | The stream lookups run again only when their properties change: deploy that region's regional stack with a new `LookupGeneration` ([§6.2](#62-stream-arn-lookup)). Don't re-create the regional stack for this, which deletes its meta and view tables. |

## 13. Checks in `generate`

Besides `validate`'s checks, `generate` refuses to write templates that would fail or lose
data when deployed.

**Against the templates it wrote last time.** When `infra.out` holds generated templates,
`generate` reads their resources and those of the new ones, and refuses to write the new
ones when:

- a view version's table in the old `regional.yaml` is missing from the new one, and
  `dynaflux.lock` doesn't mark the version retired (DF6016). Until `dynaflux retire` arrives
  in M5, no version may disappear. A lost, reverted or badly merged lock would otherwise
  delete tables the application reads;
- a view version keeps its number but its `dynaflux:fingerprint` tag changes (DF6016). A
  reverted lock that reuses a number would make the projector write rows of a new
  definition into the old version's table;
- the replica regions of the old `global.yaml` and the new `regions` differ by more than one
  region (DF6017): a Global Table update adds or removes one replica at a time;
- `regions` drops a region whose replicas have deletion protection in the old `global.yaml`
  (DF6018): run `generate --unprotect-region <region>` and deploy `global.yaml` first
  ([§12](#12-changes-after-the-first-deploy)).

The messages say how to repair the lock. To start over on purpose, delete the old templates
first. If `generate` can't read the old templates, for example after a bad hand edit, it
stops too: restore them, or delete them. These checks see only the files in `infra.out`;
`dynaflux diff` (M5) compares with what is deployed.

**`--unprotect-region <region>`** turns deletion protection off on that region's stream table
replicas in the `global.yaml` it writes: the first step of removing a region
([§12](#12-changes-after-the-first-deploy)). The region must be in `regions`. The flag
applies to one run; the next `generate` without it turns protection back on.

**No stream.** A store without a stream has nothing to deploy, so `generate` fails until the
SQL files define one.

**Limits.** A CloudFormation template holds at most 500 resources and 1,000,000 bytes, and
`generate` fails with the count and the limit. In `regional.yaml`, each archived stream adds
9 resources (16 with `split: stream`) and each view version 1 (5 when provisioned), so 25
archived streams and 60 provisioned view versions pass the limit. Roles have their own limit
([§9.5](#95-policy-size)).

## 14. Deliberate omissions

| Not in the templates | Why |
|----------------------|-----|
| Bucket access logging | It needs a log bucket outside the store. Use CloudTrail data events or a central log bucket. |
| Point-in-time recovery on the meta and view tables | They are derived state that lives and dies together ([§5.1](#51-meta-and-view-tables)): restoring one table alone breaks the views' bookkeeping. A backfill rebuilds them. |
| Customer managed KMS keys | The templates use AWS owned keys. A customer managed key needs `kms:Decrypt` for every reader, including Lambda's stream poller, and a key policy for CloudWatch Logs. |
| Reserved concurrency | A projector's concurrency follows its streams' shard count, and a reservation can fail deploys in accounts with a low concurrency quota. |
| Dead-letter queues | Only an event source mapping or CloudFormation invokes the functions, and each handles failures itself. |
| VPC | The functions call only AWS APIs; a VPC would add NAT gateway or endpoint costs. |
| An SNS topic | Pass your own as `AlarmTopicArn` ([§2](#2-parameters)). |
| A permissions boundary | One can be added to the existing roles in place when an account requires it. |
| A region check | `global.yaml` fails in a region outside `regions`, because its own region must hold a replica, and `regional.yaml` fails at the stream lookup ([§6.2](#62-stream-arn-lookup)). |

## 16. To be confirmed on AWS

This design rests on AWS documentation and on cfn-lint, without an AWS account. The
end-to-end suite ([runbooks/e2e.md](../runbooks/e2e.md)) checks the points below, and this
page will record the answers:

- Whether records trimmed from a stream after a 24-hour stall reach `aws/lambda/` in the
  bucket when the maximum record age is unlimited.
- How long a running Firehose stream takes to deliver a column added to its table.
- That Firehose writes, with `AppendOnly`, to a table that Athena created in a database that
  CloudFormation created, with the archive's value encodings.
- Where Firehose puts failed records under `errors/firehose/<stream>/`, and whether it uses
  `s3:DeleteObject`.
- Whether an in-place update of a Firehose stream's Iceberg settings, such as its buffering,
  works on a stream created with `AppendOnly`.
- Whether `<stream>_dedup` reads only the days that an `event_time` filter selects.
- Whether deletion protection blocks removing a replica. If it doesn't,
  `--unprotect-region` goes.
- Whether a new replica's initial copy of the existing items appears in its stream.
- Whether, after a `split` change, the old function's last batch on a shard can overlap the
  new function's first.
- That a failed first regional deploy rolls back cleanly and a retry succeeds.
- That `sam build` compiles the binary once for all functions, with `CodeUri` outside the
  template's folder.
- That `--import-existing-resources` adopts the retained bucket.
- That deleting a regional stack deletes the workgroup, with its query history.
- That the setup role's grants cover the optimizer calls, `iam:PassRole` included.
