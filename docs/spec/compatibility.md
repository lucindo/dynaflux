# Compatibility

This page is the v1 compatibility promise: what every v1.x release keeps compatible with
the releases before it, and what may change in any release. It covers every boundary that
Dynaflux ships, not only the Go API: your projects, the stored data, the AWS resources, the
CLI and the wire formats. Until v1.0.0, anything may still change. New features ship as
v1.x releases; a change that breaks this promise needs a new module,
`github.com/lucindo/dynaflux/v2`.

## 1. What v1.x keeps

| Surface | Promise |
|---------|---------|
| Root package, `fluxtest`, `fluxruntime` | <ul><li>Go 1 compatibility: names and signatures are only ever added.</li><li>A function never gains a parameter, variadic included. Later options on `fluxruntime.Run` or `fluxtest.NewStore` come as new functions, such as `RunWith`.</li><li>`UUID` stays a defined type, `[16]byte` ([application.md §6](../guide/application.md#6-values)).</li></ul> |
| `fluxgen` and generated code | The rules of [§2](#2-generated-code). |
| Generated names | Releases after v1.0 generate new names only for SQL constructs that v1.0 doesn't have, and `Client` never gains a method with a fixed name ([sql.md §3.2](sql.md#32-annotations)). |
| Projects (SQL, `dynaflux.yaml`) | <ul><li>A project that validates keeps validating, and generates the same API.</li><li>New warnings may appear.</li><li>A new error appears only to stop data from being lost or miscounted, and the changelog says so.</li></ul> |
| View versions | <ul><li>An unchanged definition keeps its fingerprint, so no release starts a backfill by itself.</li><li>Defaults whose change would lose data, change results or change the billing model stay: retention, archive, TTL and capacity mode.</li><li>The batching window may change in a minor release, after a measurement, with a changelog entry and `WaitFor`'s timing note updated.</li></ul> |
| Storage, resource names, logical IDs | Every v1.x release reads what any v1.x release stored. Names and logical IDs never change. |
| Catalog JSON, embedded and deployed | `MinFormatVersion` stays 1. |
| Tokens | The rule of [§3](#3-tokens). |
| `dynaflux.lock` | Format 1 is read throughout v1. |
| CLI | <ul><li>Command names, flags, exit codes and `-json` lines (`"format": 1`) stay.</li><li>Human-readable text may change.</li><li>A diagnostic code keeps its meaning.</li></ul> |
| HTTP ([http.md](http.md)) | Routes, bodies and value forms stay; fields are only added. |
| Templates | Parameters, outputs, alarm names, and metric names and dimensions stay. Resources may be added. |

The promise has no exception. These may change in any release: `explain`'s numbers and
text, the text of diagnostic messages, the packages under `internal/`, and template details
beyond the rows above.

## 2. Generated code

Generated code has a guard line that names `dynaflux.GeneratedCodeVersionN`, so the build
stops there when the library is too old for the code
([application.md §1](../guide/application.md#1-the-generated-package)).

- Code generated by a v1.x release builds with the same or any later v1.x library: every
  v1.x release keeps every `GeneratedCodeVersionN` it defined.
- A release writes a higher N whenever its code needs something the previous release lacks:
  a new catalog format, a new or changed `fluxgen` function, a new name in the root package,
  or a changed meaning. Code generated by a newer release than the library then fails at
  the guard line, not with `undefined: …` somewhere else.
- `fluxgen` only grows: a changed helper becomes a new function next to the old one.

## 3. Tokens

A `Token` is text that can pass between processes of different releases, such as during a
rolling deploy. Each release reads every token format up to its own. A release starts
writing a new format only after a release that reads it has shipped, so a rolling deploy
from the previous release never meets a token it can't read.
