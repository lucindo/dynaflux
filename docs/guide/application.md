# Writing the application

This guide covers the Go code that uses a store:

- the package that `dynaflux generate` writes
- opening a store
- appending events, reading them back and running queries
- the Go types of SQL values
- the errors, and what to do about each
- tests
- what production needs

[Concepts](concepts.md) explains the parts this page names, and
[Getting started](getting-started.md) builds a first application step by step.

The examples use the client generated for
[examples/analytics](../../examples/analytics/README.md), whose SQL is in
[its dynaflux folder](../../examples/analytics/dynaflux):

- `page_views` is a stream of page views. Its `ASYNC` views `page_daily` and `tag_hourly`
  serve the queries `PageStats` and `TagTotals`.
- `api_calls` is a stream of billable API calls with `DEDUP BY (request_id)`. Its `SYNC`
  view `quota_usage` serves the `:one` query `QuotaUsed`.

Each Go block is a file of a package `app` that builds against that client. In your module,
import your own generated package in place of
`github.com/lucindo/dynaflux/examples/analytics/internal/flux`.

## 1. The generated package

`dynaflux generate` writes the package to `go.out` in `dynaflux.yaml`, `internal/flux` by
default, and names it after `go.package`, `flux` by default
([config.md](../spec/config.md#go)):

| File | What it holds |
|------|---------------|
| `client.go` | `Client`, its constructor `New`, and the version guard. |
| `streams.go` | For each stream: its event type, such as `PageView`; its key type, `PageViewsKey`; and the methods `AppendPageView`, `AppendPageViewBatch` and `ReadPageViews`. |
| `queries.go` | For each named query: a method, such as `PageStats`, with its types `PageStatsParams` and `PageStatsRow`. |
| `catalog.go` | `Catalog`, the store's definitions, compiled. `New` and `fluxtest.NewStore` use it. |

`generate` also writes `cmd/dynaflux-runtime/main.go`, the program that every Lambda
function of the store runs, and the templates in `infra/dynaflux/`, by default. Commit them
all with `dynaflux.lock`, and don't edit them: run `go tool dynaflux generate` again after
each change to the SQL or to `dynaflux.yaml`. Each method's doc comment says what it does
for its stream or query, such as its `ACCEPT` window or its `SYNC` views.

The names come from the SQL ([sql.md §3.2](../spec/sql.md#32-annotations)):

- An event type is the stream's name in singular CamelCase, with Go's initialisms:
  `api_calls` gives `APICall`. A `-- go:type` comment before `CREATE STREAM` sets another
  name.
- A field is the column's name in CamelCase: `user_id` gives `UserID`.
- A query's method is its `-- name:`, and its types add `Params` and `Row`.
- Every event type also has the fields `EventID`, `EventTime`, `IngestTime` and
  `OriginRegion`, for the columns that Dynaflux sets
  ([sql.md §8.3](../spec/sql.md#83-implicit-columns)). An append reads only `EventTime`
  from them.

When two generated names collide, `validate` reports DF1207.

### The version guard

`client.go` holds the line `const _ = dynaflux.GeneratedCodeVersion1`. It ties the
generated code to the library releases that can run it. When a newer `dynaflux` generates
code that needs something your library lacks, it writes a higher number, and the build
stops at that line:

```text
internal/flux/client.go:11:20: undefined: dynaflux.GeneratedCodeVersion2
```

The command and the library then come from different releases. Fix it one of two ways:

- Generate with the release that `go.mod` requires: `go tool dynaflux generate`. A tool
  added with `go get -tool` is that release.
- If you run a `dynaflux` installed another way, such as with `go install`, require its
  release in `go.mod`: `go get github.com/lucindo/dynaflux@<version>`, with the `cli`
  version that `dynaflux version` prints.

`generate` warns when its release isn't the one `go.mod` requires. Code generated by an
older release always builds with a newer one: every v1 release keeps every
`GeneratedCodeVersionN` ([compatibility.md §2](../spec/compatibility.md#2-generated-code)).

## 2. Opening a store

Open one `Store` when the process starts, and share it:

<!-- doctest: go -->
```go
package app

import (
	"context"
	"fmt"
	"net/http"
	"os"
	"time"

	"github.com/aws/aws-sdk-go-v2/aws"
	"github.com/aws/aws-sdk-go-v2/aws/ratelimit"
	"github.com/aws/aws-sdk-go-v2/aws/retry"
	awshttp "github.com/aws/aws-sdk-go-v2/aws/transport/http"
	"github.com/aws/aws-sdk-go-v2/config"

	"github.com/lucindo/dynaflux"
	"github.com/lucindo/dynaflux/examples/analytics/internal/flux"
)

// newClient returns the client that every request handler of the process shares.
func newClient(ctx context.Context) (*flux.Client, error) {
	cfg, err := config.LoadDefaultConfig(ctx,
		config.WithRetryer(func() aws.Retryer {
			return retry.NewStandard(func(o *retry.StandardOptions) { o.RateLimiter = ratelimit.None })
		}),
		config.WithHTTPClient(awshttp.NewBuildableClient().
			WithTimeout(10*time.Second).
			WithTransportOptions(func(tr *http.Transport) { tr.MaxIdleConnsPerHost = 64 })))
	if err != nil {
		return nil, fmt.Errorf("load the AWS configuration: %w", err)
	}
	store, err := dynaflux.Open(dynaflux.Config{AWS: cfg, Prefix: os.Getenv("DYNAFLUX_PREFIX")})
	if err != nil {
		return nil, err
	}
	return flux.New(store), nil
}
```

- **`Config.AWS`** is used as it is: its credentials, region, retryer, HTTP client and
  endpoint. The example configures it as the store's own Lambda functions do:
  - the SDK's standard retryer without its retry quota (`ratelimit.None`). A burst of
    throttling can use up the quota, and then no call of the process retries.
  - a 10-second timeout for each HTTP attempt.
- **`MaxIdleConnsPerHost`.** The SDK keeps at most 10 idle connections to DynamoDB. With
  more calls in flight, such as hundreds of appends a second, most calls open a new TLS
  connection. Set it to about the number of calls in flight, up to the client's total of
  100 (`MaxIdleConns`).
- **The region** is `Config.AWS.Region`, here from the environment, such as `AWS_REGION`.
  The store appends, reads and queries there. It must be one of the store's `regions`;
  otherwise the first call fails before it reaches AWS:

  ```text
  dynaflux: store analytics has no region eu-west-1; its regions are us-east-1, us-west-2
  ```
- **`Config.Prefix`** names the environment: the `Prefix` that its templates were deployed
  with, such as `prod-`, or `""` for none. Read it from `DYNAFLUX_PREFIX`, which
  `dynaflux dev` prints and the store's Lambda functions read, so that one build runs in
  every environment.
- **`Open` makes no AWS call.** A missing table or grant shows on the first append, read or
  query.
- **One `Store` per process.** A `Store` and a `Client` are safe for concurrent use. One
  `Store` serves every generated package whose store is deployed with its prefix in its
  region: pass it to each package's `New`.

## 3. Appending

Each stream has two append methods, which return a `dynaflux.Token` for the events they
stored:

- `AppendPageView(ctx, ev, opts...)` stores one event.
- `AppendPageViewBatch(ctx, evs, opts...)` stores each event of `evs` as its own write, in
  order. Some events can be stored while others fail.

`EventTime` is when the fact happened. Left zero, the append uses the writer's clock. A
stream with `DEDUP BY` needs it: the append fails without it.

### Retries and DEDUP BY

On a stream with `DEDUP BY`, two appends are the same event when their `PRIMARY KEY`
values, `EventTime` and `DEDUP BY` values are equal. The second one changes nothing. It
returns `dynaflux.ErrDuplicate` with the token of the stored event, so treat it as success:

<!-- doctest: go -->
```go
package app

import (
	"context"
	"errors"

	"github.com/lucindo/dynaflux"
	"github.com/lucindo/dynaflux/examples/analytics/internal/flux"
)

// charge records an API call. Its RequestID and EventTime come from the client's request,
// so when the client sends the request again after a timeout, the retry is the same event
// and counts once.
func charge(ctx context.Context, c *flux.Client, call flux.APICall) error {
	_, err := c.AppendAPICall(ctx, call)
	if errors.Is(err, dynaflux.ErrDuplicate) {
		return nil // an earlier try stored it
	}
	return err
}
```

A retry must send the same `EventTime`. Keep the time with the request; don't take
`time.Now()` again. [The DEDUP BY recipe](dialect.md#2-idempotent-appends-with-dedup-by)
shows how to choose the key.

On a stream without `DEDUP BY`, such as `page_views`, a retried append stores the event
again, and the views count it twice. The retries that the AWS SDK makes inside one call are
safe on every stream: when the response to a write is lost, the append recognizes its own
event. Give `DEDUP BY` to a stream whose events must count once, with a key that comes with
the fact, such as a request ID ([sql.md §8.5](../spec/sql.md#85-dedup-by)).

### Batch errors

When an event of a batch fails, the error is a `*dynaflux.BatchError`. Its `Errs` line up
with the events, `nil` for each one that the call stored. A retried batch reports the
events that an earlier try stored as `ErrDuplicate`, so `errors.Is` on the whole error
can't tell a retry from a failure. Check each event:

<!-- doctest: go -->
```go
package app

import (
	"context"
	"errors"

	"github.com/lucindo/dynaflux"
	"github.com/lucindo/dynaflux/examples/analytics/internal/flux"
)

// recordCalls appends calls in up to three tries. Each try sends again only the events that
// failed. An event that fails for its content stops it, since it would fail every time.
func recordCalls(ctx context.Context, c *flux.Client, calls []flux.APICall) error {
	var err error
	for range 3 {
		_, err = c.AppendAPICallBatch(ctx, calls)
		be, ok := errors.AsType[*dynaflux.BatchError](err)
		if !ok || errors.Is(err, dynaflux.ErrInvalidValue) ||
			errors.Is(err, dynaflux.ErrOutsideWindow) || errors.Is(err, dynaflux.ErrEvaluation) {
			return err
		}
		var failed []flux.APICall
		for i, e := range be.Errs {
			if e != nil && !errors.Is(e, dynaflux.ErrDuplicate) {
				failed = append(failed, calls[i])
			}
		}
		if len(failed) == 0 {
			return nil // every event is stored, by this try or an earlier one
		}
		calls = failed
	}
	return err
}
```

An error that isn't a `*BatchError`, such as a nil option, stopped the call before it wrote
anything. The AWS SDK has already retried each write with backoff before an event fails.

### The ACCEPT window

A stream refuses an `EventTime` outside its `ACCEPT` window, measured against the writer's
clock, with `dynaflux.ErrOutsideWindow`. By default the window has no past limit and
refuses times more than 5 minutes ahead. `page_views` also refuses times more than 30 days
back ([sql.md §8.7](../spec/sql.md#87-accept-and-event-time)). The window keeps a wrong
clock from filling views with times far away.

### Importing past events

To load events from before the window, such as from a system you are replacing, append
with `dynaflux.AsImport()`:
`c.AppendPageViewBatch(ctx, views, dynaflux.AsImport())`. An import:

- skips the `ACCEPT` window, but not the limits of every value, such as times from 1970 to
  2106 ([sql.md §4.3](../spec/sql.md#43-value-restrictions))
- updates no `SYNC` view in its transaction. The projector applies the events about a
  second later, as it does for an `ASYNC` view, so a query right after the import doesn't
  see them. Append with `dynaflux.Waitable()` too, and wait for them.
- stores an event that a `SYNC` view can't compute, where a plain append would fail with
  `ErrEvaluation`. The view version then breaks, as an `ASYNC` one would.
- stores the events again when retried, into a stream without `DEDUP BY`

`dynaflux import` imports a JSON Lines file the same way
([operations.md §3.10](operations.md#310-importing-past-events)).

### Waiting for an append

An `ASYNC` view shows an append about a second later. When the next query must see it,
append with `dynaflux.Waitable()` and pass the token to the query with
`dynaflux.WaitFor` ([§5](#5-queries)). `Waitable` makes the projector write a receipt
for each event: one more write per event, so use it only where a query waits.

`WaitFor` refuses a token of more than 1,000 events. Import more in batches of at most
1,000 events, such as with `slices.Chunk`, and wait for the batches you query.

In the region of the append, a `SYNC` view shows the event as soon as the append returns,
with no wait.

## 4. Reading streams

`ReadPageViews` returns the events of one `PRIMARY KEY` value, in `(event_time, event_id)`
order, as an iterator:

<!-- doctest: go -->
```go
package app

import (
	"context"
	"time"

	"github.com/lucindo/dynaflux"
	"github.com/lucindo/dynaflux/examples/analytics/internal/flux"
)

// viewsOn returns the page views of a user on the UTC day of t, oldest first.
func viewsOn(ctx context.Context, c *flux.Client, user string, t time.Time) ([]flux.PageView, error) {
	day := t.UTC().Truncate(24 * time.Hour)
	var views []flux.PageView
	for ev, err := range c.ReadPageViews(ctx, flux.PageViewsKey{UserID: user},
		dynaflux.Since(day), dynaflux.Until(day.Add(24*time.Hour))) {
		if err != nil {
			return nil, err
		}
		views = append(views, ev)
	}
	return views, nil
}
```

- `Since(t)` reads the events at `t` or later, and `Until(t)` those before `t`. So windows
  that share an end, like these days, follow each other with no gap and no repeat.
- The iterator yields at most one error, and then stops. Leaving the loop early ends the
  read. Each `range` over it reads again.
- The read is eventually consistent: an event appended a moment before may be missing.
- It reads only the events that DynamoDB still keeps: the stream's `LOG RETENTION`, 2 days
  by default. Older events are only in the archive. Query them with Athena
  ([operations.md §8](operations.md#8-the-archive-in-athena)).

A named query over a stream, such as `RecentPageViews`, reads the same events, and can
filter, order and limit them.

## 5. Queries

Each named query is a method that takes its parameters as a struct:

- A `:many` query returns a slice of rows, such as `[]flux.PageStatsRow`, which may be
  empty.
- A `:one` query returns one row, such as `flux.QuotaUsedRow`, or `dynaflux.ErrNotFound`
  when there is none. A query that aggregates without `GROUP BY` always has one row, since
  `count()` over no rows is 0, so it never returns `ErrNotFound`.

<!-- doctest: go -->
```go
package app

import (
	"context"
	"errors"
	"time"

	"github.com/lucindo/dynaflux"
	"github.com/lucindo/dynaflux/examples/analytics/internal/flux"
)

// quotaLeft returns the units an account has left this month, out of limit.
func quotaLeft(ctx context.Context, c *flux.Client, account string, limit uint64) (uint64, error) {
	used, err := c.QuotaUsed(ctx, flux.QuotaUsedParams{AccountID: account, At: time.Now()})
	switch {
	case errors.Is(err, dynaflux.ErrNotFound):
		return limit, nil // no call this month yet
	case err != nil:
		return 0, err
	}
	return limit - min(used.UsedUnits, limit), nil
}
```

`quota_usage` is a `SYNC` view, so `quotaLeft` counts a call that `charge` has just
appended in the same region.

A parameter used with `IN`, such as `TagTotals`'s `Tags`, makes one key to read for each
value. A call may read at most 100 keys: the product of the numbers of distinct values of
its `IN` parameters. More returns `dynaflux.ErrTooManyKeys` before any read. Check the
number where the input enters your application.

### Views that aren't ready

A query over a view reads the state of the view's current version in its region. Until a
backfill has filled the version, and after it broke or was retired, the query returns
`dynaflux.ErrViewNotReady`. The error names the version, its state and the region. A
version that has just been filled can still return it for up to 30 seconds. An operator
sees the states with `dynaflux status`
([operations.md §2](operations.md#2-reading-status)).

`dynaflux.AllowPartial()` runs the query anyway. Its rows may then miss events: those that
a backfill hasn't applied yet, or every event after the version broke.

### Waiting in a query

<!-- doctest: go -->
```go
package app

import (
	"context"
	"errors"
	"time"

	"github.com/lucindo/dynaflux"
	"github.com/lucindo/dynaflux/examples/analytics/internal/flux"
)

// recordView appends a page view that happens now, and returns the stats of its page for
// today, UTC.
func recordView(ctx context.Context, c *flux.Client, view flux.PageView) ([]flux.PageStatsRow, error) {
	view.EventTime = time.Now()
	tok, err := c.AppendPageView(ctx, view, dynaflux.Waitable())
	if err != nil {
		return nil, err
	}
	day := flux.PageStatsParams{Page: view.Page, From: view.EventTime, To: view.EventTime}
	rows, err := c.PageStats(ctx, day, dynaflux.WaitFor(tok, 5*time.Second))
	switch {
	case errors.Is(err, dynaflux.ErrWaitTimeout):
		// The projector is behind: answer with rows that don't count the view yet.
		return c.PageStats(ctx, day)
	case errors.Is(err, dynaflux.ErrViewNotReady):
		// A new version of page_daily is being filled: a dashboard can show partial rows.
		return c.PageStats(ctx, day, dynaflux.AllowPartial())
	}
	return rows, err
}
```

`WaitFor(tok, timeout)`:

- waits until this region's projector has handled every event of the token, then reads
  with strongly consistent reads, so the rows count the events
- takes about the projector's batching window plus one run of it: 1 to 1.5 seconds by
  default. Give it a timeout of a few seconds.
- returns an error that matches `dynaflux.ErrWaitTimeout` when the timeout passes first,
  and the context's error when the context ends first
- fails at once, before any read, for a token:
  - of another region than the store's
  - of an append without `Waitable`
  - of more than 1,000 events
  - of an event that another region stored, as the token of an `ErrDuplicate` can be
- can wait for 24 hours after the append. The zero `Token` waits for nothing.

`ParseToken` reads a token's text, so another process of the same region can wait for it.

## 6. Values

Each SQL type has one Go type, in events, parameters and rows:

| SQL type | Go type |
|----------|---------|
| `String`, `LowCardinality(String)` | `string` |
| `UInt8` … `UInt64`, `Int8` … `Int64` | `uint8` … `uint64`, `int8` … `int64` |
| `Float64` | `float64` |
| `Bool` | `bool` |
| `Decimal(P, S)` | `dynaflux.Decimal` |
| `UUID` | `dynaflux.UUID` |
| `Date` | `time.Time` |
| `DateTime64(3)`, `DateTime64(6)`, `DateTime` | `time.Time` |
| `Nullable(T)` | `*T` |
| `Array(T)` | `[]T` |

- **`Decimal`** is exact, with at most 38 digits, and keeps its scale, the number of digits
  after its point. Make one with `dynaflux.ParseDecimal("12.50")`. A value with more digits
  after the point than its column's scale is refused, never rounded. `==` compares the
  scale too, so `12.5` and `12.50` differ; `Equal` and `Compare` compare values. All the
  values read from one column have its scale. `Big` hands the value to other libraries for
  arithmetic.
- **`UUID`** is a `[16]byte`. Parse one with `dynaflux.ParseUUID`. On Go 1.27, it converts
  to and from the standard `uuid.UUID` at no cost: `dynaflux.UUID(uuid.NewV7())`.
- **`Nullable`** columns are pointers, and nil is `NULL`. Take a pointer to any value with
  `new`: `Referrer: new("https://example.com")`.
- **`Date`** values that you pass stand for the UTC date of their instant: midnight in Tokyo
  on 2024-05-31 is 2024-05-30. Build them in UTC, with
  `time.Date(2024, time.May, 31, 0, 0, 0, 0, time.UTC)`. Dates that Dynaflux returns are
  midnight UTC.
- **Times** that Dynaflux returns are in UTC, with no monotonic clock reading, so `==`
  works on them. Times that you pass are cut to the column's precision, such as
  microseconds for `DateTime64(6)`.
- **Arrays**: nil and empty both store `[]`, and an empty array reads back as nil, so a
  test's expected value can leave the field out. An append takes at most 1,000 elements.

The generated types have no JSON tags. A `dynaflux.Token` encodes as its text in JSON, and
the zero token as `""`, so an application can hand one to a client and read it back:

<!-- doctest: go -->
```go
package app

import (
	"github.com/lucindo/dynaflux"
	"github.com/lucindo/dynaflux/examples/analytics/internal/flux"
)

// pageViewRequest is the JSON body of a page view, as a browser sends it.
type pageViewRequest struct {
	User     string   `json:"user"`
	Page     string   `json:"page"`
	Referrer string   `json:"referrer"`
	Tags     []string `json:"tags"`
}

// pageViewResponse is the answer. The browser sends the token with its next request, whose
// query waits for the view.
type pageViewResponse struct {
	Token dynaflux.Token `json:"token"`
}

// event returns the page view of r. An empty referrer is NULL.
func (r pageViewRequest) event() flux.PageView {
	ev := flux.PageView{UserID: r.User, Page: r.Page, Tags: r.Tags}
	if r.Referrer != "" {
		ev.Referrer = new(r.Referrer)
	}
	return ev
}
```

A waited query must reach the region of the append, so route a user's requests to one
region.

## 7. Errors

Errors wrap these sentinels, for `errors.Is`:

| Error | What it means | What to do |
|-------|---------------|------------|
| `ErrDuplicate` | A stream with `DEDUP BY` stored this event before. The append returns that event's token. | Treat it as success. |
| `ErrOutsideWindow` | `EventTime` is outside the stream's `ACCEPT` window. | Check the writer's clock and the time you pass. Append past events with `AsImport`. |
| `ErrInvalidValue` | A value that Dynaflux can't store, or an event too large for DynamoDB or the archive. A `*dynaflux.ValueError` names the column or query parameter. | Refuse the input: it fails again on every try. |
| `ErrEvaluation` | A query's expression failed on the rows it read, such as a division by zero, or a `SYNC` view failed on the event, and nothing was written. The error names the view version. | Fix the input, the query's parameters, or the SQL. Trying again fails again. |
| `ErrNotFound` | A `:one` query found no row. | Often a normal answer, such as "nothing yet". |
| `ErrTooManyKeys` | The `IN` parameters of a query call name more than 100 keys. | Limit the input, or split the call. |
| `ErrViewNotReady` | The view's version isn't live in the region: a backfill hasn't filled it, or it broke or was retired. | Wait for the backfill, or query with `AllowPartial`. A broken version needs an operator ([operations.md §6](operations.md#6-broken-versions-gaps-and-rebuilds)). |
| `ErrWaitTimeout` | The projector hadn't handled the token's events before `WaitFor`'s timeout. | Query without the wait, and say the numbers will update. A projector far behind shows in `dynaflux status` and the store's alarms. |

Other errors:

- **`*dynaflux.BatchError`**: some events of a batch failed. Check each one, as in
  [§3](#batch-errors).
- **The AWS SDK's errors**, such as throttling after its retries, a missing permission, or
  a missing table: check the prefix, the region and the grants.
- **A `SYNC` view row that many appends hit at once.** After about ten tries, the append
  fails with an error that names the version and the row. Retry it, or spread the load.
- **Mistakes in the call**, which fail before any I/O and match no sentinel: a nil option,
  a region that the store doesn't have, a zero `Store`, or a `WaitFor` that can't wait, as
  in [§5](#waiting-in-a-query).
- **The context's error**, when `ctx` ends first.

## 8. Tests

`fluxtest.NewStore` returns a `*dynaflux.Store` that runs in memory. Pass it to `New` in
place of a store from `Open`. Give it every catalog that the code under test uses, as one
`Store` serves several generated packages in production:
`fluxtest.NewStore(t, flux.Catalog, billing.Catalog)`. A call through a catalog it wasn't
given fails.

Run each test inside a `testing/synctest` bubble. The store's clock is `time.Now`, which in
a bubble starts at 2000-01-01 00:00:00 UTC and moves only when every goroutine of the test
waits: `time.Sleep(31 * 24 * time.Hour)` returns at once. Event IDs then repeat in every
run. In a table-driven test, call `synctest.Test` inside each `t.Run`.

<!-- doctest: go -->
```go
package app

import (
	"errors"
	"testing"
	"testing/synctest"
	"time"

	"github.com/lucindo/dynaflux"
	"github.com/lucindo/dynaflux/examples/analytics/internal/flux"
	"github.com/lucindo/dynaflux/fluxtest"
)

func TestRetriedCallCountsOnce(t *testing.T) {
	t.Parallel()
	synctest.Test(t, func(t *testing.T) {
		c := flux.New(fluxtest.NewStore(t, flux.Catalog))
		call := flux.APICall{
			AccountID: "acme", Endpoint: "/search", Units: 5,
			RequestID: dynaflux.UUID{1}, EventTime: time.Now(),
		}
		if _, err := c.AppendAPICall(t.Context(), call); err != nil {
			t.Fatal(err)
		}
		if _, err := c.AppendAPICall(t.Context(), call); !errors.Is(err, dynaflux.ErrDuplicate) {
			t.Fatalf("retry: got %v, want ErrDuplicate", err)
		}
		got, err := c.QuotaUsed(t.Context(), flux.QuotaUsedParams{AccountID: "acme", At: time.Now()})
		if want := (flux.QuotaUsedRow{UsedUnits: 5, Calls: 1}); err != nil || got != want {
			t.Errorf("QuotaUsed = %+v, %v; want %+v", got, err, want)
		}
		time.Sleep(31 * 24 * time.Hour) // to February 2000, at once
		_, err = c.QuotaUsed(t.Context(), flux.QuotaUsedParams{AccountID: "acme", At: time.Now()})
		if !errors.Is(err, dynaflux.ErrNotFound) {
			t.Errorf("QuotaUsed in February: got %v, want ErrNotFound", err)
		}
	})
}
```

What `fluxtest` doesn't model:

- **Regions.** Every event's `OriginRegion` is `local`, and nothing is copied.
- **Lag.** Every view, `ASYNC` ones included, is updated before the append returns, and
  so are receipts: `WaitFor` returns at once. Stream reads are consistent.
- **Readiness.** Every view version is live, so `ErrViewNotReady` never happens.

The [fluxtest package doc](../../fluxtest/fluxtest.go) lists every difference. To run the
application against DynamoDB Local, `dynaflux dev` serves the store and prints the
environment that points `Open` at it
([getting-started.md §9](getting-started.md#9-run-your-application-against-dev)).

## 9. Production

- **Permissions.** `generate` writes no IAM policy for applications.
  [infra.md §9.9](../spec/infra.md#99-applications) lists what an application's role needs.
  Start from the example's policy
  ([examples/analytics](../../examples/analytics/README.md#permissions)), which the
  end-to-end suite runs with, and put your store's names in it. Name a `SYNC` view's tables
  by the pattern `{base}-view-{view}-v*`: each new version of the view is a new table.
- **Regions.** Run the application in one of the store's regions, and set
  `Config.AWS.Region` to it. To serve users from more regions, run a copy of the
  application in each, with its own `Store`, and keep each user's requests in one region:
  a token can be waited for only there.
- **Environments.** Deploy each environment's templates with its own `Prefix`, and set
  `DYNAFLUX_PREFIX` to the same value for the application. The generated code is the same
  for every prefix.
- **Other languages.** The store's query function serves the queries marked
  `-- expose: http` over HTTP. [http.md](../spec/http.md) describes the requests and
  responses, and has a Python client. Appends go through the Go client or
  `dynaflux import`.
