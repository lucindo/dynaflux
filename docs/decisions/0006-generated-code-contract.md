# ADR 0006: Generated code calls six generic helpers in package `fluxgen`

- Status: Accepted
- Date: 2026-10-26

## Context

Dynaflux's design fixes what users call: `flux.New(store)`, `Append<Event>`,
`Append<Event>Batch`, `Read<Stream>`, `Import<Stream>`, one method per named query, and a
version guard. It doesn't fix how that generated code reaches the library. Whatever it
calls is public API: it can only change together with `GeneratedCodeVersionN`.

Two research prototypes proposed different contracts:

- **Store methods with `[]any` values** (`Append`, `AppendBatch`, `Read`, `Query`) returning
  a public `Row` type with `Row.Scan(dest ...any)`, as `database/sql` does under sqlc.
- **Generic helper functions** that take a `fields()` list of pointers to a struct's fields in
  catalog order and decode straight into the generated types. This prototype generated all
  three worked examples of [sql.md §12](../spec/sql.md#12-worked-examples), built and vetted
  them, and checked every field list against the embedded catalog.

The prototypes also differed on whether the catalog loader may panic and on the signature of
`fluxtest.NewStore`. Dynaflux keeps its public API small, and the root package is what users
read first.

## Decision

**Six helpers and the loader in `github.com/lucindo/dynaflux/fluxgen`,** whose package doc
says it is only for code generated by Dynaflux:

```go
package fluxgen

func LoadCatalog(data string) *dynaflux.Catalog // never panics; see below

func AppendEvent(ctx context.Context, s *dynaflux.Store, c *dynaflux.Catalog, stream string, ev []any, opts ...dynaflux.AppendOption) (dynaflux.Token, error)
func AppendEvents[E any](ctx context.Context, s *dynaflux.Store, c *dynaflux.Catalog, stream string, evs []E, fields func(*E) []any, opts ...dynaflux.AppendOption) (dynaflux.Token, error)
func ImportEvents[E any](ctx context.Context, s *dynaflux.Store, c *dynaflux.Catalog, stream string, evs []E, fields func(*E) []any, opts ...dynaflux.AppendOption) error
func ReadEvents[E any](ctx context.Context, s *dynaflux.Store, c *dynaflux.Catalog, stream string, key []any, fields func(*E) []any, opts ...dynaflux.ReadOption) iter.Seq2[E, error]
func QueryRows[R any](ctx context.Context, s *dynaflux.Store, c *dynaflux.Catalog, query string, params []any, fields func(*R) []any, opts ...dynaflux.QueryOption) ([]R, error)
func QueryRow[R any](ctx context.Context, s *dynaflux.Store, c *dynaflux.Catalog, query string, params []any, fields func(*R) []any, opts ...dynaflux.QueryOption) (R, error) // ErrNotFound
```

- `fluxgen` reaches `Store` and `Catalog` internals through `internal/access`, the hooks
  [ADR 0004](0004-runtime-storage-boundary.md) already uses for `fluxtest`. protobuf splits
  its generated-code support the same way ([protoimpl][protoimpl]).
- A `fields()` list holds pointers in catalog order: an event's declared columns, then
  `event_id`, `event_time`, `ingest_time`, `origin_region`; a key's `PRIMARY KEY` columns; a
  query's parameters or output columns. Each pointer has exactly the Go type of
  [ADR 0005](0005-public-go-value-types.md); a mismatch is an error naming the field and both
  types. No struct tags, and no reflection over struct fields: `fluxgen` checks each
  pointer's type.
- Generated methods are one line each and pass the unexported method expression
  `(*PageView).fields`, so user types gain no exported methods.
- Streams and queries are named by their SQL names.

**Every generated method ends with its options:** `Append<Event>` and `Append<Event>Batch`
and `Import<Stream>` take `...dynaflux.AppendOption`, `Read<Stream>` takes
`...dynaflux.ReadOption`, each query method takes `...dynaflux.QueryOption`. `AppendOption`
and `QueryOption` have no constructors in M2. Adding a variadic parameter later would change
each method's type, and a client would stop satisfying the interfaces users declare over it
to mock it (sqlc's `emit_interface` pattern), so the signatures are final from the start.

**Batch appends and imports** return a `*BatchError{Errs []error}` aligned with the events,
where a nil entry is a stored event, and a nil error when every event was stored.
`Unwrap() []error` returns only the non-nil entries, because the `errors` package forbids nil
in that list. Each event is its own conditional write. A single `errors.Is(err,
ErrDuplicate)` is true when any event was a duplicate, so it can't tell a retried batch from
one with a real failure; the generated doc comment of `Append<Event>Batch` shows the loop to
use instead, and a root-package test pins the difference:

```go
_, err := client.AppendChargeBatch(ctx, charges)
var be *dynaflux.BatchError
if errors.As(err, &be) {
	for i, e := range be.Errs {
		if e != nil && !errors.Is(e, dynaflux.ErrDuplicate) {
			// charges[i] was not stored
		}
	}
}
```

- The `Token` of a batch covers every event stored, by the call or, for a duplicate, before
  it, so its text grows with the batch: progress is per delivery unit, and M6's `WaitFor`
  needs each event's key.
- `Append<Event>` returns the stored event's `Token` together with `ErrDuplicate`, as
  `io.Reader` returns n with an error, so a retry can still wait for its event. A retry that
  the SDK made of the caller's own write succeeds
  ([sql.md §8.5](../spec/sql.md#85-dedup-by)).
- `Import<Stream>` skips `ACCEPT`. Into a stream without `DEDUP BY` it isn't idempotent:
  retrying after a partial failure appends the stored events again with new IDs, and its
  generated doc comment says so. `dynaflux import` goes through `internal/engine`, since the
  CLI can't call a user's generated package.

**Stream reads:** `Since(t)` is inclusive and `Until(t)` exclusive, so windows chain with no
gap or repeat. The iterator yields at most one non-nil error and then stops; each range runs
the read again with the context given to `Read<Stream>`; breaking out releases every shard's
reader.

**`LoadCatalog` never panics.** Generated `catalog.go` holds
`const catalogJSON` (the exact bytes of `catalog.Marshal`) and
`var Catalog = fluxgen.LoadCatalog(catalogJSON)`. `LoadCatalog` decodes and compiles the
catalog once, at package initialization, and keeps any error; every helper and
`fluxtest.NewStore` return it. Decoding fails only for a hand-edited file or a library older
than the generator, which the version guard already rules out at compile time.

**`fluxtest.NewStore(tb testing.TB, cat *dynaflux.Catalog) *dynaflux.Store`** takes the
catalog and no options until a test needs one. It builds the in-memory store, marks every
view version `live` (an empty store has nothing to backfill), projects each stored event
before `Append` returns so a test reads its own writes, fails the test at once on an
unreadable catalog, and fails it when a view's breaker opens. Event IDs come from a
deterministic source and are monotonic, so events appended at one instant keep their append
order and IDs repeat across runs. Time is `time.Now`, so tests of `ACCEPT` and `TTL` run
under `testing/synctest`. The package doc states how it differs from production, and the
tests of `examples/analytics` show it in use: an Example function gets no `testing.TB` and
can't start a `testing/synctest` bubble.

**Generated comments** say what the code does:
- A column with a `DEFAULT`: `// country String DEFAULT 'US': only for events stored before
  the column existed; Append stores the value given.`
- A `:one` method returns `ErrNotFound` when there is no row, except a query that aggregates
  without `GROUP BY`, which always returns one row
  ([sql.md §10.7](../spec/sql.md#107-read-time-aggregation)); its comment leaves that
  sentence out.
- A `LIMIT` parameter: 0 returns no rows.

**Other root-package API in M2:** `Store` (built by `fluxtest` in M2, by `Open` in M3),
`Catalog`, `Token` (opaque: `String`, `IsZero`), `AppendOption`, `ReadOption` with `Since`
and `Until`, `QueryOption` (its first options, `AllowPartial` and `WaitFor`, arrive in M5 and
M6), `Decimal`, `UUID`, `ValueError`, `BatchError`, `GeneratedCodeVersion1`, and the errors
`ErrNotFound`, `ErrDuplicate`, `ErrOutsideWindow`, `ErrInvalidValue`, `ErrTooManyKeys` and
`ErrEvaluation`. `ErrViewNotReady` arrives in M3 with `Open`, the first path that returns it.

**The runtime binary is M3's.** Generated `cmd/dynaflux-runtime/main.go`, its entry point
and the contents of the runtime package are designed with M3's Lambda adapter; in M2,
`generate` writes only the `go.out` package. The runtime package keeps its planned name,
`github.com/lucindo/dynaflux/runtime`, which `go.package` already can't use
([config.md](../spec/config.md#go), DF6301). A file that also needs the standard `runtime`
package imports one of them under another name ([package names][pkgnames]).

**Version guard.** `const _ = dynaflux.GeneratedCodeVersion1` sits in generated `client.go`.
Every catalog `FormatVersion` bump raises N, since catalog decoding is strict and an older
library reads no newer format, and so does every incompatible change to `fluxgen`. The library
keeps every N it still supports, as gRPC keeps `SupportPackageIsVersion3` to `9` ([grpc][grpc]).
`LoadCatalog`'s error for a catalog it can't read says to regenerate with
`go tool dynaflux generate` at the version in `go.mod`.

## Alternatives

- **Helpers in the root package:** one package fewer, but seven names meant only for
  generated code would sit next to about fifteen user-facing ones, inviting calls like
  `dynaflux.QueryRows` with hand-built `[]any`. The hooks a separate package needs already
  exist.
- **`Store` methods with `[]any` and a public `Row` with `Scan`:** familiar from
  `database/sql`, but it adds a public `Row` type, generated code needs a loop per query to
  scan, and stream reads yield rows instead of typed events.
- **Reflection over struct tags:** slower, and errors appear at run time instead of in a
  generator test.
- **Options added when first needed:** each addition breaks interfaces declared over the
  client.
- **`MustLoadCatalog` panicking at init,** as `regexp.MustCompile` does: idiomatic for
  constants, but the project rules out panics in library code.
- **`fluxtest.NewStore(t)` without the catalog:** the store would learn the catalog on first
  use, so a test that queries before its first append would find no live versions.
- **A runtime package named `fluxruntime`:** it never shadows the standard `runtime`, but
  the design already names the package `runtime`, and `go.package` already reserves that
  name.
- **`runtime.Run` and `main.go` in M2:** M2's code generation scope doesn't include them,
  and `Run` would only report "not implemented", fixing M3's adapter API before it is
  designed.

## Consequences

- `fluxgen` documents seven functions. Their signatures are part of `GeneratedCodeVersion1`.
- The whole three-domain example generates about 14 KB of Go plus the catalog literal.
- Codegen and `fluxgen` take each SQL type's Go type from one table, `internal/gotype`, so
  the types generated code declares are the ones `fluxgen` decodes into.
- The public API gains `fluxgen`, options on every generated method, and `Decimal`, `UUID`
  and `ValueError` in the root package. The runtime entry point, planned as
  `runtime.Start`, is designed in M3.
